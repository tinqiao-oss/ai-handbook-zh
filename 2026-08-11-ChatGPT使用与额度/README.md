## 这期讲了什么

把所有任务都扔给同一个入口，是额度烧得快的主要原因。这期讲清楚三件事：Chat、Work 和 Codex 分别该在什么时候用；全局、项目和本地这三处的记忆与自定义指令是什么关系；以及一套把准备阶段留在 Chat、执行阶段才进 Work 或 Codex 的工作流，实际能省下多少额度。

---

## 一、三种工作方式怎么选

2026 年 7 月改版后，原来的 Codex 客户端并入了 ChatGPT 客户端，网页端一分为二变成 Chat 和 Work。现在是 Chat、Work、Codex 三种工作方式。

**它们不是三个模型，是三种工作方式。按你最终要的成果来选：**

| 模式 | 成果 | 网页 | 客户端 | IDE | CLI | 主要场景 |
|---|---|---|---|---|---|---|
| Chat | 一个回答或一轮讨论 | √ | √ | × | × | 查资料、解释概念、比较方案、判断方向 |
| Work | 一个可以审核、修改和继续使用的成果 | √ | √ | × | × | 报告、文档、表格、PPT、研究分析、工作计划 |
| Codex | 一次面向开发环境的工作 | √ | √ | √ | √ | 读仓库、改代码、跑命令、测试、diff、Git |

### 一个常见的误区

有种说法是「Work 是给不懂代码的人编程，Codex 才是给程序员用的」。**这个区分不准确。**

判断标准不是你会不会写代码，而是**任务需不需要直接进开发环境**：

- 完全不懂代码，但任务要操作仓库、运行命令和测试 → 还是应该用 Codex
- 是程序员，但最终要交付的是一份报告或表格 → Work 往往更合适

## 二、额度是怎么算的

- **Work 和 Codex 共用同一套 Agent 额度**，Chat 有自己单独的用量规则
- Agent 额度随套餐级别升高而增多
- 同样一件事交给 Codex，通常要读文件、跑命令、来回好几轮，比 Work 更容易把额度吃掉

所以额度有限的时候，把不同类型的任务交给正确的入口，本身就是在省额度。

> 具体哪个套餐能用哪些模型、额度是多少，这部分变动很快，以你当前看到的页面为准。

## 三、记忆和自定义指令放在哪

一共两种东西，三个位置。

**两种**：由 ChatGPT 自己维护的是**记忆**，由你主动填写的是**自定义指令**。
**三处**：全局、项目、本地。

| 信息层级 | 主要作用 | 位置 | 用于 | 适合放什么 |
|---|---|---|---|---|
| 全局记忆 | 跨 Chat 和 Work 召回有用背景 | 云端 | Chat + Work | 全局稳定偏好、长期背景、常用工作方式 |
| 全局自定义指令 | 跨聊天稳定执行 | 云端 | Chat + Work | 回答语言、格式要求、长期规则 |
| 项目记忆 | 项目内部的独立记忆 | 云端 | Chat + Work | 本项目的稳定偏好和长期背景 |
| 项目自定义指令 | 项目内部的独立指令 | 云端 | Chat + Work | 本项目的目标、术语规范、输出格式 |
| Codex Memories | 本地 Codex 的独立记忆 | 本地 | Codex | 本机的开发习惯和历史工作上下文 |
| AGENTS.md | 给 Codex 的明确指令 | 本地 | Codex | 全局开发规则、仓库规范、测试要求 |

> AGENTS.md 实际上分两层：放在用户目录下的对这台电脑上的所有项目生效，放在仓库里的跟着仓库走、可以提交给团队共用。表里的「本地」指的是前者。

### 用两个问题判断该放哪

**第一个：这是背景，还是规则？**

- **记忆**是系统从过去的交流里带回来的背景
- **自定义指令**是你明确要求它长期遵守的规则

「我不懂代码，讲得浅显一点」是长期偏好，交给记忆召回就行；「改完代码必须运行测试」是明确规则，应该写进自定义指令或 AGENTS.md。

**第二个：它应该在哪个范围生效？**

- 跨对话都可能用到的个人背景和通用偏好 → 全局
- 只在这个项目里成立的目标、术语和输出格式 → 项目自定义指令，**它优先于全局**
- 只对这台电脑的开发习惯和规则 → 本地

### 项目记忆有两种模式

| 模式 | 能看到什么 | 什么时候选 |
|---|---|---|
| 仅限项目记忆 | 不引用项目外的已保存记忆和聊天，但可以用当前项目里的聊天、文件和指令 | 项目涉及敏感资料，或者不希望其他上下文混进来 |
| 默认记忆 | 可以使用账号侧的已保存记忆 | 项目需要你的长期个人背景和偏好 |

⚠️ **这个选择在创建项目时做，之后改不了。** 想换只能新建一个项目。

### 三个都叫「自定义指令」的入口，是三个不同的东西

| 在哪里 | 管的是什么 | 作用范围 |
|---|---|---|
| 网页版 → 个性化 | 账号级自定义指令 | 跟着账号走，Chat 和 Work 都用 |
| Codex 网页端 | 云端 Codex 指令 | 只影响云端的 Codex 任务 |
| ChatGPT 客户端 | 本地 AGENTS.md | 只对这台电脑 |

名字完全一样，存储位置、同步范围和影响的产品都不一样。改之前先确认你打开的是哪一个。

### 账号记忆目前只能在网页版管理

客户端里那个 Memories 入口管的是**本地 Codex 记忆**，不是账号记忆。账号记忆要去网页版 → 右下角账户名 → 个性化 里管理。

那里能看到的只是**记忆摘要**，完整内容不显示。想知道它到底记了什么，可以直接在对话框里问它，也可以要求它记住或忘掉某些内容。

## 四、省额度的工作流

一个复杂任务通常可以拆成三个阶段：

| 阶段 | 要解决什么 |
|---|---|
| 准备 | 目标是什么、交付物是什么、有哪些限制、需要哪些资料、怎样才算完成 |
| 执行 | 真正编写文档、制作表格、修改代码、调用工具、运行测试 |
| 验收 | 检查结果、修复问题、优化内容、整理归档 |

**需求还比较模糊的任务，准备阶段可以先放在 Chat 里完成。** 用 Chat 探索需求、比较方案、补齐资料，直到自己确认方向，然后让它把讨论结果压缩成一份任务书（[提示词在这里](提示词/把讨论压缩成任务书.md)）。

任务书完成后，再按交付物选执行环境：报告、文档、表格、PPT 交给 Work；进仓库、改代码、跑命令和测试交给 Codex。

**两个好处：**

1. 前期讨论不占用 Work 和 Codex 共用的那套额度
2. 执行阶段拿到的是一份边界清楚的任务书，不需要重新陪你发散，也不会被大量已经放弃的讨论干扰

**讨论中被否决的方案不用全部删掉**，但只保留「方案已否决 + 一句原因」，别把整段来回拉扯带进执行阶段。这样既保持上下文干净，也避免执行时重新踩一遍同样的坑。

### 这不是所有任务都要套的仪式

需求已经很明确的时候，比如改一个确定位置的小问题，直接交给 Codex 反而更省事。

这套流程最适合的是：**需求还不清楚、方案存在取舍、后续执行又需要大量工具**的复杂任务。

### 任务书不是圣旨

目标、约束和验收标准应该保持稳定，但具体实现遇到困难时，仍然可以调整方案。

## 五、AI 给的数字，值得多问一句

实测中让 Codex 估算这套工作流省了多少额度，它第一次回答「大约 30% 到 40%」。追问「你确定认真计算了吗，给我看详细数据」之后，它承认前面只是经验判断、没有真正计算，重新算完给出的区间是 **10% 到 20%**。

两点提醒：

- **第一个数字是它顺口给的。** 哪怕用的是最强模型、最高推理强度，也一样。要一个结论时，顺手要一下它的计算过程，成本很低。
- **第二个数字仍然是估算。** 它算的是「如果全程用 Codex 会花多少」，而这个对照从来没有真实发生过。所以这里可信的是方法，不是那个具体数字。
