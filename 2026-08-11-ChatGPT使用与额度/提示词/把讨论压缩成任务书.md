# 把讨论压缩成任务书

**用在哪**：在 Chat 里把需求聊清楚之后，方案定了、关键问题也答完了，准备交给 Work 或者 Codex 执行之前。

**怎么用**：整段复制，发在这条讨论的末尾。

---

```
把我们这段讨论压缩成一份任务书，交给一个完全不知道前情的执行者。

要求：

1. 只写已经确认的结论，不要复述讨论过程。
2. 讨论中被否决的方案，只保留“某方案已否决”加一句原因，不要展开。
   目的是让执行者不再重新踩一遍，而不是让他读完整段来回。
3. 按下面的结构写，每一项都要有。确实没有的写“无”，不要自己编：

   - 任务目标
   - 已知背景
   - 工作范围（明确写出哪些不做）
   - 已有资料
   - 约束条件
   - 交付物
   - 验收标准
   - 禁止事项
   - 需要停下来找我确认的节点

4. 直接在对话里输出全文，不要生成文件、附件或下载链接。
5. 用词要具体到能判断是否达成。不要用“优化”“完善”“提升体验”这类
   无法验证的说法。
```

---

## 几个提醒

**第 3 条里的“工作范围”要写清楚哪些不做。** 这一项最容易被忽略，但它是执行阶段过度设计的主要来源。

**第 4 条不是多余的。** 让它生成文件，有时候会给出一个打不开或者下载不了的链接，还得再要一次。直接让它发在对话里，复制起来最省事。

**第 5 条也不是多余的。** 验收标准如果写成“效果更好”，执行者做完了你也没法判断算不算完成。

**确认节点的数量要自己拿捏。** 节点太少，等你发现方向走偏，它已经做了一大半；节点太多，等于又回到你一步步指挥它。一般设在“方向可能走偏”和“做下去就不好回头”这两类位置上。

**拿到任务书之后自己读一遍。** 它压缩的时候可能会漏掉你在讨论中途改过的决定，尤其是那些你只说了一句就带过的调整。
